# Production-Grade Agent Instructions & Project Rules

Welcome, Agent! This file outlines the absolute must-follow rules and production-grade design principles for this repository. Adhere to these instructions strictly when modifying code or introducing new features.

---

## 🛠️ Core Tech Stack

- **Language**: Go (Golang)
- **HTTP Framework**: [Echo v4](https://echo.labstack.com/)
- **DB Client**: PostgreSQL via `pgx/v5` with connection pooling (`pgxpool`)
- **Query Generator**: [SQLC](https://sqlc.dev/) for type-safe database queries
- **DB Migrations**: [Goose](https://github.com/pressly/goose)
- **Caching**: Redis via `go-redis/v9`
- **Validation**: [go-playground/validator/v10](https://github.com/go-playground/validator)
- **Structured Logging**: Uber Zap (`internal/logging`)

---

## 🏗️ Layering & Architectural Integrity

Follow the layered architecture strictly:
1. **`cmd/api/main.go`**: Entrypoint. Initializes connections (Postgres, Redis), registers middlewares, and handles graceful shutdown. Do not put route controllers here.
2. **`internal/router/`**: Map routes to controllers and apply path-specific middlewares (JWT, rate limiters).
3. **`internal/controllers/`**: Receives Echo context, validates inputs, formats standardized API responses, and forwards tasks to Services. Keep business logic out of controllers.
4. **`internal/dto/`**: Data Transfer Objects for request binding and response presentation.
5. **`internal/services/`**: Houses all core business logic. Must be completely decoupled from Echo (`echo.Context`). Use `context.Context` parameters to propagate cancellation and deadlines.
6. **`internal/db/`**: Auto-generated by SQLC. Do not edit.

---

## 💾 Database & SQLC (Production Standards)

- **No Inline Raw SQL**: Never write raw SQL strings in Go files.
- **SQLC Schema**: Define all Postgres operations in `database/queries/*.sql`. Run `make sqlc` to generate bindings.
- **Database Migrations**: Define migrations in `database/schema/*.sql`. 
  - *Rule*: Never edit an applied migration file. Always create a new sequential migration for alterations.
- **Database Transactions (Atomicity)**:
  - If a service method executes multiple sequential DB mutations (e.g. creating a user and initializing their wallet), you **MUST** run them inside a database transaction (`pgx.Tx`).
  - Implement a transaction coordinator/helper or pass the transaction-wrapped `db.Querier` instance.

---

## 🔒 Security & Secrets

- **Zero Hardcoded Secrets**: Do not store credentials, JWT secrets, keys, or API tokens in the codebase. Always read them via `utils.Config` (which parses environment variables).
- **Outbound HTTP Calls**:
  - Never use the default HTTP client (`http.DefaultClient`) as it lacks default timeouts.
  - Always instantiate a custom client with a strict timeout (e.g., `Timeout: 5 * time.Second`).
- **CORS Configuration**:
  - In production, restrict CORS strictly to exact trusted domains (via `Config.FrontendURL` or `Config.AdminURL`). Never use wildcard `*` origins in production.
- **Secure Middleware**:
  - Use secure HTTP headers (e.g., X-Frame-Options, X-Content-Type-Options, Content Security Policy) via Echo's secure middleware.

---

## 🛡️ Validation, Error Handling, & Logging

- **Input Validation**:
  - Validate all inputs on DTOs using `c.Bind(dto)` and `c.Validate(dto)`.
  - Use specific constraints (`min`, `max`, `email`, `required`) in struct tags.
- **Error Sanitization & Propagation**:
  - Log internal errors (with exact Postgres/stack traces) via Zap logger (`internal/logging`).
  - Do not leak raw database error messages (like constraint violations) to the end-user. Return sanitised messages and standardized error responses.
- **Structured Logging**:
  - Always use `internal/logging` (`Infof`, `Errorf`, etc.) instead of standard `fmt.Println` or `log.Println`.
  - Pass structural context parameters where appropriate.

---

## 🧪 Testing & Parallelism

- **Directory Mirroring**: Organize integration/E2E tests under the `/tests` root directory, mirroring the `/internal` package structure (e.g., `tests/controllers/`).
- **Parallel Execution**:
  - Always use `t.Parallel()` for isolated unit tests to speed up check times.
  - Avoid `t.Parallel()` for database or cache-mutating integration tests to prevent race conditions or transactions conflict.

---

## ⚡ Concurrency & Context

- **Context Propagation**: Always pass `c.Request().Context()` down to the service layer, Postgres, and Redis calls. This ensures database queries are terminated if the client disconnects.
- **Graceful Shutdowns**:
  - Cleanup resources (`CloseDB`, `CloseRedis`) gracefully on shutdown signals.
  - Allow a timeout period (e.g., 10 seconds) for active requests to drain before quitting.

---

## 🔍 Pre-flight Code Verification

Before concluding any work, you must run:
1. `make sqlc` to check query generation and types.
2. `go fmt ./...` and `go vet ./...` to ensure clean syntax.
3. `go test -v ./...` to verify all tests pass.
4. `go build -o /tmp/build-check cmd/api/main.go` to confirm the application builds.

## 📝 Git Commit Conventions (Conventional Commits)

Always write standard, structured commit messages adhering to the **Conventional Commits** specification:

- **`feat:`**: A new feature (e.g., `feat: add rate limiter middleware`)
- **`fix:`**: A bug fix (e.g., `fix: resolve db connection pool memory leak`)
- **`docs:`**: Documentation-only changes (e.g., `docs: add testing strategy docs`)
- **`refactor:`**: Code changes that neither fix a bug nor add a feature (e.g., `refactor: extract routes from main`)
- **`chore:`**: Maintenance tasks, dependencies, build/tooling changes (e.g., `chore: add golangci-lint configuration`)
- **`test:`**: Adding or modifying test suites (e.g., `test: add unit test for user model`)
- **`style:`**: Code formatting, styling, or formatting (e.g., `style: run go fmt`)
- **`perf:`**: Changes aimed at improving performance (e.g., `perf: optimize redis cache query`)

---

## 🔄 Workflow & Contribution Constraints

- **No Auto-Commits & No Auto-Pushes**: Agents (and developers) must never perform automatic Git commits or push code directly to the repository branches. All changes must be made locally and pushed manually by the developer, or submitted strictly via **Pull Requests (PRs)**.
- **PR-Only Submissions**: Direct commits to production branches (`main`/`master`) are strictly prohibited.
- **Test Coverage**: No strict test coverage percentage conditions are enforced. However, all new features should be accompanied by relevant test cases, and the existing test suite must compile and pass cleanly.
